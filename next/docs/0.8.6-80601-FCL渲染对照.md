# 80601 与 FCL 的实际渲染对照

2026-10-23 核对 FCL 官方当前提交 `617d0aa14f1ce1e25b0b7710f0db520774d0c27b`，以及原接入提交 `a36e1e42292d6a67c93be0dafbfdceff01823e71`。这里只对照当前使用的 NG-GL4ES 通道，不把它等同于 FCL 的 Zink 等其他通道。

| 项目 | 核对结果 |
| --- | --- |
| 上游渲染产物 | 当前 FCL 的 `NG-GL4ES-release.aar` Git blob 仍是 `c5f55f1f4e1ce42b894b6e8fba543ef483a3eb4a`，与接入时相同 |
| 本地 ARM64 库 | `libng_gl4es.so` SHA256 为 `cfee8bf238fc508478454c2daf19b518182827b426d5d4556f1e93a0ad348ea7`，与 FCL AAR 内原文件一致，未修改该二进制 |
| 纹理函数 | HXZ 的 GLX 分发未替换 `glTexSubImage2D`，直接转交上述 NG 库，不是另写了一套纹理更新实现 |
| 显示 | 同为 EGL Surface 直接提交；HXZ 当前通道没有 GPU 像素读回或 CPU 整帧复制 |
| 环境 | ES3、MC 颜色、法线、整数重载、错误查询兼容参数与 FCL 的 NG 配置一致。FCL 的 `LIBGL_MIPMAP=3` 位于旧 GL4ES/VGPU 分支，不能挪到 NG 分支当作通用性能修复 |
| 保留的差异 | HXZ 的目标 GL 3.3 用于新版 Minecraft；当前 FCL NG 配置为 3.1。HXZ 另有游戏进程隔离、Surface 生命周期保护、基顶点索引和 16 纹理槽边界修复，不为追求表面完全一致而移除 |

对 `glTexSubImage2D` 的两次 Java 栈采样仅能确定进入了纹理更新，不能证明是哪种资源、转换路径或驱动调用耗时。NG 的“AutoMipMap forced”是其自身初始化输出，也出现在同源实现中，不能把它直接当成 HXZ 误设的环境变量。精简诊断现在保留越过 LWJGL、GlStateManager、NativeImage 后的两个游戏调用点，以区分初始化图集和持续的动画更新。

因此，本轮已修复有确定复现的社区恢复阻塞；渲染卡顿尚未得到设备侧修复证明，也没有实测 60 FPS。不能把再次复制同一份库或本地主机测试当成手机性能修复。
