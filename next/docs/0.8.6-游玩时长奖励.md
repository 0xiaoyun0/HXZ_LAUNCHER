# 0.8.6 累计游玩时长奖励

每累计 **24 小时经可信游戏服核验的游玩时长，获得 5 积分**。例如已核验 23 小时 59 分 30 秒，再核验 30 秒即到账 5 积分；后续完整的 24 小时继续发放。时长按毫秒记账，展示时换算成秒，不会在每次心跳舍弃不足一秒的余数。

不足 24 小时的进度跨日、跨周和社区服务重启保留。每周在线时长排名继续展示，但名次不再产生奖励；不设每周最低参与时长，不设每日奖励计时上限。新奖励计入实际到账当周的积分榜，并沿用现有积分年度汇总。

管理端「游玩时长奖励」只提供奖励开关、固定比例说明、累计奖励到账记录和旧版周榜结算记录。开关立即生效。关闭期间仍核验、保存时长；重新开启时补发尚未到账的完整 24 小时奖励，余数继续保留。一次补发多个完整周期时，合并积分与一条站内信，记录覆盖的周期序号。

## 核验边界

- 仅接收通过可信游戏服鉴权和格式检查的在线名单。以社区服务器当前时间为准，只核验同一游戏服前后两次在线名单都出现的玩家。
- 相邻心跳间隔不超过 90 秒才形成确认时段。超过 90 秒的间隔整体丢弃，离线、服务停机期间不补记；重启后的第一条心跳只建立基线。
- 同一 UUID 的大小写、连字符写法统一，跨服、多设备、重复心跳的重叠时段取并集。北京时间零点和周一会切分记录，累计奖励进度不因此重置。
- 服务器时钟回退时不接受新时段，也不在回退时间发放待处理奖励，等时钟追平后继续。客户端提交的时长、累计遥测统计、显示名称不能增加奖励或重定向钱包；奖励身份来自社区成员 UUID。
- 这里的「真实游玩」指服务器核验的在线时长。在线名单不包含操作活跃信号，因此无法识别全部挂机，不承诺完整反挂机。

## 旧数据迁移

首次启动 0.8.6 时在 SQLite 事务中建立累计账户与迁移标记。后续启动不再重复导入。

1. 旧积分钱包、积分流水、站内信、时长日历、逐段明细、周榜结算快照和旧规则表原样保留。
2. **存在旧 `playtime_settlements` 记录的整周时长不导入新奖励账户**，包括当周关闭奖励、未达到最低时长、排名未获奖等结算结果为零的情况。已按旧规则结算的周期不会再次支付，也不会重新计算或追回旧奖励。
3. 尚未结算的历史周期和当前周，导入 `playtime_days` 中已经核验的原始毫秒数，旧的每日周榜上限不截断这些原始记录。累计满 24 小时即按新规则到账，余数保留。旧版未结算周不再补发名次奖励。
4. 奖励开关继承升级时当前已生效的旧规则；旧版排队等待下周生效的排名配置停止生效。升级后只使用固定比例和立即生效的开关。

示例：甲在已结算旧周有 48 小时并获得 100 积分，在尚未结算的周有 25 小时。升级保留原来的 100 积分，再按新规则发 5 积分，剩余 1 小时。若另外一个已结算周有 24 小时但旧奖励为零，该 24 小时也不会重复导入。

`playtime_accounts` 保存累计毫秒数与已支付的完整周期数。新增核验时段只把时段并集增加的差额写入账户。发放时，账户支付游标、积分钱包/流水/当周汇总、`playtime_awards` 到账历史与去重站内信在同一 `BEGIN IMMEDIATE` 事务中提交。任何一项失败都会回滚发放，已核验时长继续保留供重试；重复执行和服务重启不会重复到账。

## API 兼容与新增字段

`GET /api/playtime/calendar`、`/api/playtime/detail?date=YYYY-MM-DD` 和 `/api/playtime/leaderboard?week=...` 都新增当前登录者的 `rewardSummary`，与正在查看的日期/周无关，不允许通过 `uid` 参数查看他人私有进度：

```json
{
  "scheme": "cumulative-24h",
  "enabled": true,
  "intervalSeconds": 86400,
  "pointsPerInterval": "5",
  "verifiedSeconds": 90000,
  "accountedSeconds": 86400,
  "awardedIntervals": 1,
  "earnedPoints": "5",
  "pendingIntervals": 0,
  "progressSeconds": 3600,
  "remainingSeconds": 82800,
  "nextRewardPoints": "5"
}
```

`verifiedSeconds` 是本方案可计奖的累计核验时长，排除旧已结算周期；`earnedPoints` 只表示本方案已经到账的积分，旧周榜奖励仍在历史结算和积分流水中。`accountedSeconds` 是已支付周期覆盖的秒数。`progressSeconds` 为不足一周期的余数，`remainingSeconds` 为距下一个完整周期的秒数，整周期边界返回 86400。关闭奖励时 `pendingIntervals` 可能大于零，表示完整但暂未支付的周期。账户不受日历最近 365 天的展示范围限制。

日历的 `summary` 额外提供相同的 `earnedPoints`、`progressSeconds`、`remainingSeconds`。既有 `seconds`、`eligibleSeconds`、日历、明细 `sessions`、周榜名次和历史周列表保留；新方案中 `eligibleSeconds` 等于原始核验秒数，不再使用旧每日上限。明细不暴露游戏服来源标签。

周榜增加顶层 `rewardScheme`：旧结算快照为 `legacy-weekly`，新方案为 `cumulative-24h`。新周榜每项保留 `reward: "0"`、`eligible: true`，并增加 `rewardScheme: "cumulative-24h"`；`reward` 仅为旧名次奖励兼容字段，不能用它表示本人的累计收益。旧快照的 `reward`、`eligible`、规则与排名保持原样。`settled` 和 `settledAt` 继续表示旧周榜是否实际结算，新方案不生成旧周榜结算。

当前规则对象为 `{enabled, scheme:"cumulative-24h", intervalSeconds:86400, pointsPerInterval:"5"}`，另保留弃用兼容字段 `minWeeklyMinutes:0`、`dailyCapMinutes:1440`、`rewards:[]`，不再作为可配置奖励条件。

`PUT /api/admin/playtime/rules` 接收 `{ "enabled": true }`，立即生效；尝试改变新比例字段会被拒绝。旧最低时长、上限、排名字段即使被旧客户端提交也不参与新规则。响应保留 `rules`、`effectiveWeek` 并增加 `effectiveAt`；`effectiveWeek` 为当前周，不再表示下周生效。

`GET /api/admin/playtime/rules` 保留 `rules`、`nextRules`、`effectiveWeek`、旧 `settlements` 和核验说明；`nextRules` 等于当前规则。新增 `effectiveAt` 及最近 200 条 `awards`，每条包含 `{id, uid, name, first_interval, last_interval, points, created}`，其中周期序号从 1 开始，积分为十进制字符串，时间戳为毫秒。
