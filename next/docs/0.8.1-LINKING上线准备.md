# 0.8.1 LINKING 上线准备

本文件是发布前检查与执行顺序，不表示剧情已经上线。升级客户端或社区服务端不会自动发布章节，也不会替玩家完成任务。桌面随包提供的管理员只读预览不连接玩家进度，不发放外观或物品。

管理员在 LINKING「管理活动 → 章节与档案」顶部可直接看到「正式上线准备」清单：选择承接的开头，查看原章、接续及两卷的准备、未发布与已发布状态，再进入原有编辑器审阅。清单不会自动创建或发布，创建及发布仍需逐项确认并校验草稿版本；「同步上线状态」只读取服务器状态。若旧服务无法提供正式版本摘要，界面显示待核验，不能把草稿当成正式剧情。普通玩家仍按服务器公开状态、排期和任务前置进入。

## 执行顺序

1. 停服并一致性备份完整数据目录、环境配置与现有程序；运行中的 SQLite 不可仅复制主数据库文件。部署包含本次音乐门禁修复的服务端与客户端，先验证原章和已有玩家数据完整。
2. 管理员重新读取活动配置、章节列表、原章草稿与正式版本。导出当前原章和两卷状态，核对作者未发布编辑。后续写操作必须使用本次读取的草稿 revision；遇到 409 则停止，重新读取与人工合并。
3. 原章完全没有续写时，使用编辑器的原章续写操作（`POST /api/admin/linking/story-expansion`），传入原章 ID 与当前 revision。它同时追加白枝、音乐和灯标续写，不需要再重复追加音乐或灯标。如果已有部分续写，只在核对缺项后使用音乐或灯标追加接口，不重新导入完整续写。
4. 原章草稿具备 `snow-ash-light-signal` 后，使用「创建两卷续篇草稿」（`POST /api/admin/linking/volumes-expansion`），传入最新原章 revision。它仅创建两个未发布草稿，同时把原章 revision 加一以防并发修改；原章正文与任务不被重写。
5. 逐章检查正文、任务、纪念物定义、前置与排期。管理员预览只用于阅读检查。尤其确认原章原有未发布编辑已由作者审阅，不可因上线续篇而顺带发布未核准内容。
6. 使用各章最新 revision，先发布原章，再发布第一卷，最后发布第二卷。发布接口为 `POST /api/admin/linking/chapters/{id}/publish`。发布源版本必须包含导入两卷后增加的原章 revision。
7. 普通测试账号检查原章、音乐任务前后、灯标审核前后和跨卷前置。确认未解锁正文不可读取，未解锁音乐账户无样式选择；完成音乐任务后出现一次解锁提示，两端可返回经典播放器，其他账号不受影响。

这里列出的 POST 均会改变线上内容，只在完成上述复核并准备正式上线时执行。准备检查本身不调用这些接口。

## 门禁、幂等与恢复

音乐外观只接受当前登录社区的 `/api/linking/features` 成功响应。服务端从正式章节及玩家完成记录授予 `music-archive`，草稿、目录查询和管理控制台只读预览不授予效果；客户端没有管理员音乐外观旁路。本地仅保存经典/档案偏好及首次提示记录，旧版缓存中的 `earned` 不再作为依据。账号、社区或连接状态变化会清除当次确认；请求失败回到经典界面，音乐库和播放能力保留。

首次服务器确认解锁后，桌面与 Android 音乐页展示解锁提示。提示记录按社区与账号隔离，在当前设备显示一次；应用关闭动画或系统要求减少动态效果时使用静态提示。清除本机应用数据可能再次显示提示，不会重新发奖。Android 使用轻量档案外观，不加载桌面三维场景。

原章追加操作与两卷创建操作在标识已存在时返回 409，不重复导入或覆盖；两卷创建、物品检查及源 revision 校验在同一事务中完成。跨章依赖在发布时检查循环、缺失任务及归档引用。外观以账号和效果唯一保存，物品领取以账号、章节和任务唯一保存，重复阅读、审核或领取不能重复发奖。

已正式赚取的外观记录在活动维护、章节关闭或后续调整时保留。若上线后需撤回内容，先保留数据并记录当前版本；需要归档时按第二卷、第一卷的逆依赖顺序处理。不要删除玩家进度、奖励记录或直接回写旧数据库。涉及恢复原章前置任务时，应先解除后续正式章节对它的引用并重新审查，避免留下不可完成的章节。

本次验证包括隔离服务端任务/审核/奖励/前置测试、门禁竞态测试及桌面和 Android 网页组件检查。它不替代正式服务重启后的验收或实体 Android 设备测试。
