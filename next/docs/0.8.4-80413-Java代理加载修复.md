# Android 80413 · Java 代理本地库启动修复

80412 的设备报告在 EGL/NG 初始化之后、HotSpot 初始化期间退出：
`Could not find agent library instrument ... libinstrument.so not found`。
这条证据不表示游戏已经运行，也不能把本次退出归因于 GPU。

已核实发布的 80400 运行模块同时包含 Java 21/25 的 `libinstrument.so`。
其 ELF 依赖包括 `libjli.so`、`libjava.so`、`libjvm.so`，具有正确的 SONAME。
80412 的进程只尝试更新动态库搜索路径，没有预加载 `libjli` 和
`libinstrument`。ART 创建的进程不能假定运行后 `setenv(LD_LIBRARY_PATH)`
就能重新配置 Android 应用链接器命名空间。

## 修复

- 在共同的 `hxz_java` 入口以当前 Java 的绝对路径预加载 libjli，再加载
  libjvm 与 Java 核心库。存在 Java agent 时预加载 libinstrument，并验证
  同一命名空间按 SONAME 查找成功后，才进入 JNI_CreateJavaVM。
- 指定当前 Java 的 `sun.boot.library.path`，移除可能残留的旧引导库路径；
  不覆盖游戏原生库的 `java.library.path`。
- 保留所有 `-javaagent` 参数及顺序。没有改成 `-agentpath`：HotSpot 对
  Java agent 另有 java.instrument 模块解析和 JPLIS 处理，不能简单替换。
- 缺失或加载失败在 VM 致命退出之前返回具体 dlopen 错误；诊断给出 Java
  登录组件提示，不建议删除游戏或改用软件渲染。

参考的 FCL `FCLauncher.setUpJavaRuntime` 先按绝对路径加载 JLI、JVM、
核心库，再遍历运行时共享库。本次仅预载启动需要的核心及代理库，
不递归加载不需要的调试或 AWT 组件。

## 验证边界

命令：`node scripts/tests/android-jvm-agent084.mjs`。

运行真实 `hxz_jvm.cpp`，模拟 Android 封闭的本地库搜索边界：未预载的
SONAME 查找失败。修复前重现报告中的 instrument not found，修复后通过
单代理、双代理、无代理、缺失 JLI、缺失 instrument、损坏 instrument 六种
场景。验证代理参数和游戏原生库路径保留，缺失依赖时不会调用 VM 创建。

该检查不是 Android 真机 HotSpot 执行；没有宣称实机帧率或整合包启动验收。
完整 Android Release 编译、签名及 APK 依赖另外检查。
