# OSMesa 共享槽直出：源码可行性审查

审查日期：2026-10-21。范围是保持游戏独立进程，研究能否让 OSMesa 在 swap 时把图像导出到已经保留的共享槽，省去 HXZ 的 scratch→shared CPU 拷贝。本次只读源码、形成设计约束，没有修改 native/Mesa 实现，没有运行图形探针或实机测试，因此下文区分源码结论和待验证项。

## 结论

**共享槽 acquire/submit/cancel 可以安全设计；但现有 Mesa 上，“swap 前把输出地址改为槽→glFinish→恢复 scratch→发布”不能作为通用正确的实现直接落地。** 同尺寸、同格式重绑地址确实保留内部帧缓冲；问题是 `glFinish` 不承诺再次向一个新地址导出完整图像。

明确反例：游戏在 scratch 上绘制后先调用 `glFlush` 或 `glFinish`，随后没有新绘制就 swap。第一次调用已经把内部图像导出到 scratch，并把 Mesa 的 `rb->defined` 清为 false。swap 时重绑新槽再 finish，Mesa 会跳过导出；共享槽中的旧内容或初始内容被误当作新帧发布。连续无绘制的 swap 也有这个问题。当前流程仍会将保留在 scratch 的图像复制进槽，因此这个反例会构成新回归。

需要先有“无论脏标记如何，都把保留的默认颜色附件完整导出到指定槽”的可靠机制，或经过完整 GL 状态保存/恢复的显式读回方案，再讨论 lease 接入。单纯的 lease 并不能补足图像语义。没有采用 FCL 代码，也没有据此宣布性能提升。

## Mesa 的实际语义

1. **重绑同尺寸不清屏，也不导入目标内存。** [`OSMesaMakeCurrent` 第 759–783 行](../.runtime/hxz-runtime-upstream/sources/mesa-25.3.4/src/gallium/frontends/osmesa/osmesa.c#L759) 只有格式/宽高变化才销毁并重建 osmesa_buffer；其余只是更新 `map` 地址并重用 drawable。785–787 的注释直接说明并未实现从用户内存载入 framebuffer。`st_manager.c:1068–1102` 按 drawable ID 重用 gl_framebuffer，218–230 在 drawable stamp 未变时跳过资源验证。故相同尺寸格式的 scratch↔slot 切换本身保留颜色和深度附件；**恢复到 1×1 dummy 会重建附件，不能这样恢复。**
2. **这里不是 Gallium 直接渲染进共享内存。** `osmesa.c:29–43` 描述普通 Gallium 资源和 flush 时复制；[`osmesa_read_buffer` 第 186–216 行](../.runtime/hxz-runtime-upstream/sources/mesa-25.3.4/src/gallium/frontends/osmesa/osmesa.c#L186) 对资源做 `PIPE_MAP_READ`，逐行 memcpy 到 map。未来最多删除 HXZ 的 scratch→shared 拷贝；Mesa 内部资源→用户目标的拷贝和宿主 shared→ANativeWindow 拷贝仍然存在。
3. **finish 等待渲染，但有条件地导出。** [`st_cb_flush.c:77–85、105–111`](../.runtime/hxz-runtime-upstream/sources/mesa-25.3.4/src/mesa/state_tracker/st_cb_flush.c#L77) 先 flush 和等待 fence，再调用 frontbuffer 导出。[`st_manager.c:1209–1217`](../.runtime/hxz-runtime-upstream/sources/mesa-25.3.4/src/mesa/state_tracker/st_manager.c#L1209) 仅在 `rb->defined` 为真时调 frontend，成功后设 false。`st_atom_framebuffer.c:149–167` 在下一次绘制状态更新时设真；同上下文 MakeCurrent 只安排状态更新，不执行绘制；`_mesa_Finish` 只排空已有顶点和 finish。不能通过 `glFinish` 的返回值判断是否真的导出了（返回类型 void）。
4. **当前用户 FBO 会影响导出。** [`context.c:1499–1525`](../.runtime/hxz-runtime-upstream/sources/mesa-25.3.4/src/mesa/main/context.c#L1499) 明确保留用户 Draw/Read FBO；`st_manager.c:1186–1190` 从当前 DrawBuffer 获取 winsys framebuffer，若当前是用户 FBO就返回。重绑 OSMesa 地址不会自动选择默认帧缓冲。这也是当前 HXZ/FCL 路径应另行回归的既有边界。
5. **行长、方向和后处理必须单独处理。** `osmesa.c:386–398` 根据 `OSMESA_ROW_LENGTH` 和 `OSMESA_Y_UP` 导出；PixelStore 不替调用方检查槽容量。槽 stride 是共享内存约定值；恢复 scratch 时必须恢复它自己的 row length，不能沿用较大的共享 stride。`osmesa.c:364–383` 可能就地运行 `pp_run(res,res,...)`；强行反复触发原 flush_front 可能重复应用后处理，不能把直接调用该回调视作完成设计。

上游 `test-render.cpp:246–286` 的 `separate_buffers_per_context` 测试在重绑后还特意做一次屏幕外绘制以触发实际 flush，并验证上下文保留的颜色。这与上述语义一致，但它不是本次反例的执行结果；本次没有运行该测试。

## 可接受的 lease 生命周期

建议只公开一个不可复制 token；它携带 session、generation、非零 sequence、slot、width/height/stride/capacity/base 和映射 State 的强引用。token 始终由拥有 current context 的渲染线程操作，ACK 线程仅通过受保护状态机改变已发布状态。不能把现有 `pending==sequence` 扩展后直接同时表示“预留”和“已发送”。

`FREE → RESERVED → BOUND → READY → IN_FLIGHT → FREE`

- **acquire：** 以原子或锁操作独占空槽，冻结该帧 generation、尺寸和容量；两槽都占用时保持 scratch 并丢弃显示帧，不能覆盖等待 ACK 的槽。查验 stride≥width、尺寸正值、RGBA 地址对齐及容量计算无溢出。这里不向宿主发布 FRAME。
- **BOUND：** 仅在确认 context 是当前且同尺寸同格式时改变输出地址。成功后 State 必须存活，不能由 IPC stop/resize 顺手 munmap；也不能让另一线程同时使用这个 context。GL 目标指针可能被 frontend 的后续 flush 使用，不能仅以“此处 memcpy 已结束”判断生命周期。
- **READY：** 可靠导出完成、所有渲染/读回工作已完成，且已恢复同尺寸 scratch 和 scratch 的 stride/方向之后才能进入。两次 MakeCurrent 都要检查，不能忽略失败。恢复失败时隔离槽、context 和映射并停止该路径，不能释放槽让宿主/其他帧并发读写它。RAII 清理也必须遵守这个顺序。
- **submit：** 核验 token 没有失效/重复提交；在发布协议的锁保护下协调 generation 与连接状态，确保 FRAME 元数据对应实际导出尺寸。CPU 写入先完成，再通知宿主。`SOCK_SEQPACKET` 的发送与共享内存 CPU 可见性需按 Android/Linux 平台约定落实；进程内的 `std::atomic` 不能代替跨进程协议，更不能把 `msync` 当作渲染同步。发送成功后槽归宿主读取阶段，直到匹配 session/slot/sequence 的 ACK；**ACK 超时不是可重用条件。**
- **ACK：** 必须拒绝 RESERVED/BOUND 阶段的提前 ACK、陈旧或重复 ACK；精确核验已发送 sequence，避免新 lease 被旧 ACK 释放。现有 host 在同步 `hxz_present_frame` 返回后发 ACK（`hxz_ipc.cpp:87–96`），这个“读共享槽已完成”的条件应保留。它不需要等待屏幕 compositor 显示完成，因为宿主已经复制进另一块 native buffer。
- **cancel：** 仅允许未发布并已安全脱离 GL 指针的 lease；取消两次、跨 session 取消或取消已发布帧都应失败。发送失败也必须先脱离 GL 地址，再清空预留。发生断连时停止复用旧 session；已发送槽不能因超时转入新 session，旧映射保留至所有本地绑定和操作释放。
- **resize/销毁：** 已保留 token 固定 generation；尺寸变化在脱离 slot 后应用，不能在绑定期间重分配 scratch/映射或用错误尺寸恢复。旧 generation 的帧可取消；若 resize 与已经发布的帧交错，宿主可继续按旧帧丢弃并 ACK（现有机制如此）。surface 生命周期与共享映射生命周期分开，不能持全局/UI 锁等待 glFinish 或 ACK。

## 后续方案选择

可研究维护一个范围很小的 Mesa 导出扩展：显式完成渲染，从保留的默认颜色附件向指定 CPU 目标做完整快照，独立于 `rb->defined` 和当前用户 DrawBuffer，同时明确后处理是否已经执行。它仍是一次 Mesa 内部读回，不能宣传为零拷贝。需要审查维护成本、导出失败路径和许可证，当前没有写此扩展。

另一种候选是显式 `glReadPixels` 写入租约槽；它必须保存/恢复 read framebuffer、read buffer、pixel pack buffer 与全部影响输出的 pack 状态，处理上下文版本/扩展、方向和格式/后处理差异，再比较耗时。它不是单纯的 MakeCurrent 方案，也尚未验证。通过临时伪绘制“弄脏”附件来强迫导出会引入状态与渲染副作用，不作为方案。

## 实施前必须通过的回归

1. 图像语义：完整清屏；仅局部更新并保留未绘制区域；深度/模板跨同尺寸重绑；swap 前 glFlush、一次/多次 glFinish；连续不绘制 swap。每个槽先填不同哨兵，逐像素比较现有 scratch 路径输出，防止偶然读到同色旧帧而误通过。
2. GL 状态：用户 draw/read FBO 在 swap 时保持绑定；从默认 FBO 回切；多个 context 交替、共享对象、线程迁移；改造前后应用的 GL 状态一致。候选 readPixels 路径另覆盖 PBO、pack row length/alignment/skips/swapbytes 和核心/兼容上下文。
3. 内存布局：奇数宽高、stride>width、方向0/1、填充 guard 字节、尺寸上限和乘法溢出；小→大→小 resize、generation 交错、surface 失效/重建。两次重绑的尺寸必须正确且恢复后继续绘制不得破坏旧槽。
4. lease：两槽饱和、延迟/重复/陈旧/提前 ACK、重复 submit/cancel、acquire 后和 finish 中断连、发送失败、恢复 scratch 失败、渲染异常退出。用受控宿主延迟读取与槽校验和检查“发布后不再写”和“ACK 前不复用”，验证映射强引用与卸载顺序。
5. 实际驱动：在最终打包的 Mesa 构建上分别验证 llvmpipe/softpipe 及已支持的 zink 路径；源码单元推理不能替代驱动回归。首先可做本机 CPU Mesa 的针对性探针，不要求用户实机操作。
6. 性能：保持尺寸、渲染负载和丢帧条件一致，测量 swap/导出 CPU 时间、端到端延迟、共享槽等待与复制字节量。只有确认删除 scratch→shared，且没有另增读回/状态同步开销后才能声称收益；宿主复制仍在。

当前建议：**保留现有路径；将此项记为受图像导出契约阻挡的候选优化，不在 0.8.4 中未经验证替换。**
