# 0.8.6 棋类响应与小游戏检查

本轮覆盖当前街机目录中的 16 项游戏，以及五子棋、中国象棋、国际象棋三种棋桌。发现并修复两类问题：棋类搜索超过预期思考时间；扫雷仅保证首步安全，之后可能卡在无法按单个数字继续推理的局面。没有把射击、生存和随机构筑游戏标记为“所有种子都保证通关”。

## 棋类：保留车万女仆算法，减少等待

使用仓库已有的 [TouhouLittleMaid 固定提交](https://github.com/TartaricAcid/TouhouLittleMaid/tree/8a3ac5e9eacf0c6d63adf8832949f3ce81484fe6/src/main/java/com/github/tartaricacid/touhoulittlemaid/api/game) 引擎。搜索、评估和剪枝继续来自上游，不另写棋类 AI。上游来源、MIT / Apache / GPL 许可证和可重建源码随引擎保留，见 `third_party/maid-board-engine/README.md`。

原来的国际象棋和中国象棋搜索只在完成一个完整深度后检查时间；某个深度计算较久就会超时。另外，为取得备用落子，协议层会再次初始化并重复搜索。五子棋也会按多个深度重复启动已经自带迭代加深的上游搜索。

现在通过可选回调上报每个**完整深度**的结果。服务端逐一检查候选是否合法，在 220 / 320 / 450 / 650 / 850 毫秒的五档搜索等待预算到达时，交付最近完成的合法结果，并结束独立计算进程。国际象棋与中国象棋各只启动一次迭代搜索；五子棋先执行上游的廉价战术预判，再进行一次深层搜索。五档最大深度、候选宽度的区别保留。设备较慢时，高档可能只完成较浅深度，不能据此承诺固定棋力或 Elo。

进程启动另计 5 秒上限；CPU 竞争导致首次候选迟到时，最多额外等 2 秒，首个合法候选一到立即交付。只有一个合法走法的局面直接返回。HTTP 落子接口继续立即返回玩家落子后的棋局和 `thinking` 状态，机器人结果由后台进程交付。

同一台 Windows 机器、相同开局和中盘局面，分别调用 0.8.5 发布目录引擎与本轮引擎。下面是第五档两个局面的平均墙钟耗时，包含独立 Node 进程启动：

| 棋类 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 国际象棋 | 2822 ms | 909 ms |
| 中国象棋 | 2296 ms | 959 ms |
| 五子棋 | 3154 ms | 1046 ms |

共 30 组“棋种 × 开局/中盘 × 五档”配对测量，均校验返回走法。每行只测一次，受当时 CPU 负载影响，低档部分样本并未变快；这不是跨设备延迟保证。完整记录在 [基准 JSON](evidence/0.8.6-board-benchmark.json)，复测命令：`node scripts/tests/board-benchmark086.mjs`（需要保留本地 0.8.5 服务端基线）。

## 扫雷：生成后先认证数字推理可解

旧版种子 2、首格 54 是回归样例：按已开数字的“剩余雷数为零 / 等于未开邻格数”和全局雷数规则操作，会卡住。这只说明此推理策略不能继续，不能单凭该结果认定旧棋盘在数学上绝对无解。

新版最多尝试 64 次确定性布局，只接受能够用上述可见信息完成所有安全格的棋盘。认证器不会用隐藏格的雷值来选择下一步；只在推导某格安全之后模拟翻开它。若尝试次数耗尽，则使用远离首格的边缘雷区布局，首格的零区展开可触达全部安全格。这个兜底只针对当前固定的 9×12、20 雷规则。

20 个种子 × 全部 108 个首格，共 2160 盘，用另一套独立玩家策略实际执行插旗与翻格，全部完成 88 个安全格；额外测试固定随机源耗尽重试的兜底路径。一次单独生成扫描中最慢约 30 ms。错误插旗、错误和弦展开仍然可能踩雷，规则不会代替玩家排除操作失误。

生成、回放、分段回放和客户端/服务端副本一致；旧冻结 v8 及更早规则未修改。电脑和手机的新客户端请求**规则协议 10**，服务端在开始游戏时选定并保存对应回放引擎，分段同步和最终结算始终使用同一个引擎。旧规则 9 的扫雷代码与冻结 v8 完全相同，因此规则 9 扫雷继续使用 v8 生成器；其他规则 9 游戏保持本轮修改前的行为。这是小游戏协议版本，不是应用版本。

| 客户端与服务端组合 | 行为 |
| --- | --- |
| 旧规则 8/9 客户端 → 新服务端 | 扫雷按原来的布局重放与结算，兼容旧客户端。 |
| 新规则 10 客户端 → 新服务端 | 使用经过逻辑认证的新布局，正常同步与结算。 |
| 新客户端 → 不支持规则 10 的旧服务端 | 提示更新社区规则，退回本机练习；不把新生成器的输入作为旧规则排名成绩提交。 |

混版 HTTP 测试固定种子 2，使新旧布局必定不同，分别完成规则 8、9、10 的首步、分段同步、重发同步、通关与重复结算，并检查所有其他规则 9/10 游戏。双端控制器测试实际调用开始流程，确认发送规则 10，遇到旧响应或拒绝请求时退回练习模式。

| 游戏 | 本轮检查范围与结论 |
| --- | --- |
| 月光迷宫 | DFS 主树保证道路连接，追加环路不会断路；20 种子 × 100 关检查所有星屑和守卫出生点可达，未发现隔离目标。该检查不代表避开守卫必然成功。 |
| 星灯迷宫 | 20 种子 × 30 房检查出生点、全部敌人、宝箱与出口位于同一通路；通过实际关卡切换入口生成下一房，未发现墙内目标。测试清除敌人仅用于触发生成，不作为实战通关证据。 |
| 打砖块 | 100 关均有可破坏目标；钢墙不计入通关剩余数量，清除可破坏砖后可以推进至第 100 关。布局结构检查不等于任意反弹轨迹都能清关。 |
| 林间疾跑 | 障碍宽高、间隔与最高速度有界；检查固定输入回放，没有发现新增生成错误。无尽玩法没有最终通关条件。 |
| 俄罗斯方块 | 七袋出块、暂存、旋转与消行逻辑检查；确定性回放通过。玩家堆叠方式会导致失败，不保证任意操作可救。 |
| 云朵 2048 | 相同数字每次只合并一次、无变化输入不生成新块；原有经典规则回归覆盖。随机落点不保证必达 2048。 |
| 青柠贪吃蛇 | 果实只在空格生成，禁直接掉头，允许移动到本步会腾出的尾格；原有规则回归覆盖。玩家可能围出无法救回的局面。 |
| 星堡双卫 | 生成、墙体/出生位置和关卡数量检查，固定输入回放通过。未证明所有操作策略可守住基地。 |
| 花园守卫 | 路径固定，建筑避开道路，敌人和建造操作有界；固定输入回放通过。布塔/售塔选择可影响后续资源，未声称每种布局都可过三十波。 |
| 星庭流萤 | 弹数上限、速度增长、受伤保护及固定输入回放检查。无尽弹幕仍可能超过玩家能力。 |
| 苍穹航线 | 关卡结束、升级池、弹体上限检查；原有 24 项升级效果及回放回归通过。未承诺每种随机构筑都能完成百关。 |
| 星潮幸存 | 出生边界、数量上限、升级暂停及回放检查。生存玩法不定义全种子必胜。 |
| 星图旅札 | 牌库洗牌、抽牌/弃牌、能量与遭遇升级流程检查，固定输入回放通过；没有证明所有牌序都有获胜策略。 |
| 骰光远征 | 沿用已有多策略完整运行回归：谨慎策略 24/24 胜、激进策略 1/24 胜，表明决策影响结果；保留骰子与敌意变化。 |
| 风帆补给线 | 沿用已有完整航行回归：谨慎策略 24/24 胜，激进策略 0/24 胜；低补给时的应急停泊仍可用，不改积分/奖励公式。 |
| 三种棋桌 | 五档合法落子、一手将杀、五子棋立即成五和单端必防、后台交付、权限及棋谱回放回归通过；不保证机器人对任何局面都能获胜。 |

## 验证

`third_party/maid-board-engine` 中执行 `mvn -B -ntp package` 成功，再以 `node scripts/sync-board-engine.mjs` 同步生成模块和对应源码。`node scripts/sync-games.mjs` 同步电脑、手机及服务端共享规则。

新增 `board-latency-086.test.mjs` 和 `arcade-fairness-086.test.mjs`，结合既有启动、棋规、后台对局、棋谱、街机升级和 0.8.3 完整航行测试运行。假时钟测试精确验证 850 ms 交付边界、最近合法候选、非法候选过滤及迟到首候选；实进程测试覆盖五档战术和合法性。墙钟性能数字使用独立基准，避免把 CI 繁忙程度当成算法正确性。

协议兼容回归：`node --test --test-concurrency=1 apps/community-server/test/arcade-protocol-086.test.mjs apps/community-server/test/arcade-083.test.mjs`。该命令验证混版回放与结算、双端协商、新服务端保留规则 8/9、既有战术游戏及完整航行行为。
