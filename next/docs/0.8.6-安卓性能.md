# 0.8.6 Android 原生渲染性能

本次针对 FCL EGL / NG 的实际 GLX 绘制路径减少 CPU 函数查找和索引缓冲上传。没有更改 FPS 上限、账号或整合包玩法模组。扩展预算仍默认关闭；另修复了该功能加入时意外改变关闭状态下自动内存分配的回归。

当前没有连接 Android 设备；用户按下方流程手动验证游戏帧率。**本机回归不能证明小米或 vivo 达到 60 FPS，也不能证明此前 1–2 FPS 的全部原因已经消除。**

## 已确认的热路径开销

生产代码为 `mobile/runtime/native/hxz_fcl_render.cpp`，通过现有 GLX 回归夹具直接调用，不是另写一套算法代替生产实现。

1. `safeDrawBaseVertex` / `safeDrawInstancedBaseVertex` 每次绘制重复解析 GL 函数。模拟 GL 的 10,000 次相同实例绘制实际累计 90,000 次 `dlsym`。
2. 即使原始 EBO 内容、基顶点和数量没有变化，兼容修复仍每次 `glBufferData` 重新分配/上传提升后的 32 位索引。相同夹具实际累计 10,000 次上传。
3. 来源读取沿用 NG 的 CPU 影子缓冲，不是帧缓冲像素回读。已核对本地上游 `src/gl/buffers.c:gl4es_glGetBufferSubData` 的 `memcpy` 实现；本次没有引入 GPU 像素复制。

这两项重复工作已通过计数回归确认。GPU 负载、驱动差异、模组渲染/区块生成、实际帧时间仍需实机区分；不能把已确认的局部开销当作 1–2 FPS 的唯一根因。

## 实现与兼容性

- 缓存进程内只加载一次的 renderer 函数入口；不会缓存跨上下文变化的纹理能力查询结果。
- 每次绘制仍重新读取当前 EBO，并检查其范围和映射状态。在提升索引时逐项比较实际结果；只有完整结果相同时才跳过上传。没有仅按 EBO ID、offset 或长度猜测内容不变。
- 实际内容、base 或数量变化时重新上传；上下文切换、销毁及地址复用后也重新创建并初始化临时缓冲。
- 仅复用现有单个临时缓冲和向量，没有增加随区块数量增长的缓存。轮流绘制不同索引结果时仍需要上传，不能承诺这类场景的上传次数降低。
- 保留 uint16 基顶点溢出的 32 位索引修复、实例数量、源 EBO 绑定恢复、无效参数委托以及 16 槽纹理边界保护。没有通过关闭图形兼容修复换取性能。
- FCL/NG 二进制、GPL 标记及第三方授权保持原状。本次修改的是 HXZ 的适配器。

## 可重复的本地验证

在仓库根目录运行：

```powershell
node scripts/tests/android-performance086.mjs
```

该入口使用 `-O2` 编译生产适配器与原有 GL 缓冲夹具，依赖仓库现有 Zig host 工具和 Android NDK 头文件。可用 `HXZ_ANDROID_NDK` 指定 NDK。无须手机、游戏账号或网络。

修复前先运行新增断言，已得到明确失败：

```text
METRIC repeated_draws=10000 symbol_lookups=90000 index_uploads=10000
FAIL steady-state draws must not resolve GL symbols again
```

修复后要求：

| 真实适配器调用场景 | 额外函数查找 | 额外索引上传 |
| --- | ---: | ---: |
| 预热后 10,000 次相同实例绘制 | 0 | 0 |
| 预热后 250 次绘制，每次 49,152 个索引 | 0 | 0 |

第二项避免重复提交 49,152,000 字节的索引数据。测试同时验证同一 EBO 原地改写、base/count 改变、新上下文、旧地址复用都触发正确上传；检查实例数量和最终索引结果，而不只检查“没有崩溃”。原有字节/短整型索引、越界、负 base、零实例、primitive restart、多绘制和纹理单元边界测试也继续执行。

输出 `host_us` 仅用于观察当前电脑上的夹具耗时，不设置依赖机器速度的断言，不表示设备 GPU 耗时或 Android FPS。

## 用户手动帧率验证

1. 同一设备使用同一整合包版本、存档/服务器、地点、视角和画质。关闭“内存扩展”，记录渲染分辨率、视距、模拟距离以及屏幕刷新率。旧版和新版必须保持这些值一致，避免把画质降低计作代码收益。
2. 分别测试轻量实例与实际玩法整合包。进入同一地点等待资源和区块加载稳定；至少预热 3 分钟，再打开 F3 调试屏幕记录 60 秒，每秒记录一次 FPS。站立和连续移动各测一次。加载阶段另记，不混入稳定场景结果。
3. 对比旧构建与 0.8.6，最好按旧→新→旧重复，控制温度和后台应用。记录是否出现水面、地形、透明物体花屏；vivo 必须单独检查原来的图形问题。

## 扩展预算关闭后的分配回归

用户报告加入扩展内存后卡顿，对比提交 c8183e0 与其父提交发现：自动模组堆由“当前可用内存的 45%，最多 4 GiB”变成“总内存的 45%，最多 6 GiB”。后者即使开关关闭也生效；它不是系统交换内存开关失效，而是关闭路径也改变了自动堆预算。

12 GiB 总内存、4 GiB 当前可用的回归夹具，旧规则为 1,843 MiB，问题规则为 2,560 MiB。0.8.6 恢复按当前可用物理内存计算的自动基线，并保留 Android / 原生图形余量；只有明确开启时才增加最多 1 GiB、受实际空闲交换空间约束的预算。手动内存设置仍受物理余量上限约束。更大的 Xmx 只表示上限，不能直接证明实际换页或 FPS 变化。

**node scripts/tests/android-memory-budget084.mjs** 执行 94 项检查，包括不同物理余量、ON→OFF 的最终 Xmx 替换，以及关闭后忽略所有交换空间。运行移动开发服务后，**node scripts/tests/android-memory-preference086.mjs** 驱动实际 Vue 设置，验证开启、关闭、重新打开页面、再启动时向原生层传递 false。

设置在**下次启动游戏**生效，不能缩小已经运行中的 JVM。应用不执行 swapon/swapoff，也不能阻止 Android 自己换页；系统内存扩展选项仍由系统控制。这项代码回归已复现并修复，是否是用户设备低帧率的全部原因仍待同场景实测。
