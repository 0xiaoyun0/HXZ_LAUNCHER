## 4. 建议实施顺序

以下为 HXZ 独立设计建议，收益是基于瓶颈的推断，需第 5 节的基准验证。

1. **先统一语义。** 所有入口默认官方优先、总预算 32。把来源的优先级与健康状态分开；官方正常时镜像请求数应为零；持续超时/失败后才允许备用。用户主动选择镜像加速时可使用另一套延迟竞速策略，仍计入同一预算。若 Node 与 Java 安装任务确需重叠，采用主进程统一许可或明确拆分相加不超过 32 的额度；仅把两者各设 32 不够。
2. **合并重复资源和请求。** Node assets 在排队前按哈希和大小去重；同一目标+哈希的并发调用共享一项下载。每个消费者独立取消，最后一个消费者退出才取消底层传输；不同哈希争用同一目标应报错。Java 已有 assets 去重，重点是库和跨任务共享。对应第 2 节“同目标任务合并”和第 3 节“去重”。
3. **让已有并发真正用于不同文件。** Java 不为全部备用源提前占线程；第一候选失败或触发备用条件才提交下一候选。镜像竞速最多两条流并可按大小/排队压力关闭。统计传入网络字节与校验后有用字节，避免用重复流量营造速度提升。对应第 2 节源选择、第 3 节竞速。
4. **自适应分段与能力缓存。** 保留有权威哈希、精确范围和原子发布要求；先确认官方对象的长度和 Range 行为，再按队列压力决定 1/2/4 段或受限追加。Range 失败时记短期能力结果，不为后续文件重复探测。Zulu 大包可从同一官方响应获取准确 Content-Length/Content-Range 后启用分段；没有可靠长度就继续流式下载，不按文件名或舍入 size 猜值。适度延后尾段拆分，防止吞吐已充足时增加握手和合并 IO。对应第 2 节分段、RFC Range、第 3 节 Zulu。
5. **安全重试与恢复。** 保留指数退避、抖动和 Retry-After；增加 If-Range、完整范围检查、416 重启，避免把损坏段反复拼回。若要持久续传，需有内容身份、校验器、完成区间、临时文件大小和写入完成边界的日志；重启后重新验证，再决定复用。实现前不要把“继续安装任务”称为“所有文件跨重启断点续传”。对应第 2 节断点与第 3 节现状。
6. **并行安装分支。** 版本元数据就绪后，本体、依赖、资源索引同时进入共享队列；索引到达便提交 assets。native 提取等依赖文件完成即可执行，CPU/磁盘另用小预算；全部必需分支成功后才组装/发布实例。Forge/NeoForge 处理器保留输入依赖，不整体无条件并行。已有“单一阶段字符串”的进度结构要改成分支统计，防止多个 phase 相互重置。对应第 2 节安装依赖图与第 3 节安装阶段。
7. **扩展已校验内容复用和公共元数据缓存。** 先利用已有根目录和 Zulu 内容缓存，再根据基准决定是否建立跨目录 CAS。下载完成原子写入不可变缓存，安装到目标后仍保证篡改不会污染其他实例；共享可写硬链接不是默认安全选择。公共 GET 支持条件请求，有权威哈希的二进制按哈希复用。对应第 2 节两类缓存。

不建议把“更多线程”“所有源一直竞速”“所有文件四分段”“无条件跳过哈希”作为速度目标。任务时间同时受吞吐、请求延迟、CDN 限制、校验/磁盘和安装依赖关系影响；上游默认数值不直接当 HXZ 的最优值。
