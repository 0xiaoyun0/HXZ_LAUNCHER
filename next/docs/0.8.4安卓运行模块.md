# 0.8.4 安卓应用内运行模块

本轮把 FCL fork 作为社区 APK 内的 Android library，首次运行游戏时下载 JRE、LWJGL、JNA、Cacio 等运行资源。没有第二个游戏引擎应用，没有把 FCL APK 改名后交给 DexClassLoader，也不通过 Android 安装器安装运行资源。社区应用更新仍是正常的 APK 更新。

固定上游为 FoldCraftLauncher `efe4dcc5dbc78c55be177c330239e12845ae7ccf`。维护源码在 `.runtime/fcl-source/FoldCraftLauncher-efe4dcc5dbc78c55be177c330239e12845ae7ccf`；可重放的 HXZ 修改在 `mobile/game-engine/src`、`apply-adaptation.mjs`、`prepare-embedded.mjs`。本轮不以编译结果宣称设备或进服兼容性；用户已要求不进行实机测试。

## 选择依据

FCL 的界面直接依赖 `R`、ViewBinding、主题、`Application`、已声明的 Activity/Service 和 `nativeLibraryDir`。`DexClassLoader` 负责加载包含 DEX 的 JAR/APK 类，不替调用方注册 Activity、替换 Application 或合并 Android 资源表。单纯重命名现成 APK 无法满足这些条件。[Android DexClassLoader](https://developer.android.com/reference/dalvik/system/DexClassLoader)

Android library 可以包含代码、资源和 manifest，由宿主构建时合并。因此保留 FCL 设置、触控和渲染界面的实际实现，把 Android 代码/资源及必要 JNI 静态纳入社区；运行资产通过专门的文件接口读取。这也避免手工注入 Android 资源 package ID 和反射修改 framework classloader。[Android library](https://developer.android.com/studio/projects/android-library)

官方 on-demand feature 方案依赖 App Bundle、Play Feature Delivery 和 SplitCompat，不能把一个独立 FCL APK 当成任意渠道可直接激活的 split。[Play Feature Delivery](https://developer.android.com/guide/playcore/feature-delivery)、[on-demand delivery](https://developer.android.com/guide/playcore/feature-delivery/on-demand)

Android 14 对 target 34+ 应用动态加载 DEX/JAR/APK 增加只读要求，官方建议从可信来源校验完整性并使用应用内部存储。本方案不动态加载 Android DEX；本地复制的联机 JVM agent 仍在打开输出流后、写入内容前置为只读，下载模块必须在签名、归档散列和逐文件校验后激活。游戏 JVM 中的 JAR 不替代 APK 中 Android Activity 的代码。[Android 14 DCL](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading)、[动态代码安全](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading)

## 宿主契约

`mobile/game-engine/android-library` 使用原 FCL 的 Java/Kotlin、资源和 CMake。`prepare-embedded.mjs` 生成 `.runtime/embedded-runtime`：基础 assets、去运行资源的 vendor AAR、资源覆盖以及私有进程 manifest。vendor 旧 `libglxshim.so` 被剥除，使用 fork 中相同 SONAME 的源码构建版本。游戏 vendor JNI 和 CMake 为 ARM64；宿主不做全局 ABI 过滤，其他 ABI 的社区功能仍可安装运行，游戏入口由设备支持检查拒绝。

宿主 `CommunityApp` 继承 `com.tungsten.fcl.FCLApp` 并调用 `super`。FCLApp 在 attach 时设置当前 Application，在 onCreate 中初始化目录和生命周期回调；这条路径没有 `System.loadLibrary`。社区进程不因此加载游戏 JNI。

FCL Activity 和普通后台服务在 `:game`；安装器 JVM 在 `:jvm`，图形探测在 `:hxz_graphics`，崩溃页面保留 `:crash`。这些是同 UID 的私有应用进程，不是 `isolatedProcess=true`：后者会丢失读取私有游戏文件和使用应用权限的条件。游戏进程独立不会隔离同 UID 的数据访问权。[Activity process](https://developer.android.com/guide/topics/manifest/activity-element#proc)

社区通过同包 explicit Intent 启动 `com.tungsten.fcl.hxz.HxzBridgeActivity`，继续使用 `job` JSON 协议 1。嵌入 manifest 将该入口及 FCL Activity 设为 `exported=false`，不增加第二个 launcher 图标；FCL 原升级检查在社区包名下改为提示前往社区设置，避免再安装 FCL APK。

运行模块激活后的目录必须位于 `getFilesDir()` 下，结构为 `root/app_runtime/**`。宿主写入：

```java
getSharedPreferences("hxz-runtime-module", 0).edit()
    .putString("root", verifiedGenerationAbsolutePath).commit();
```

在尚未启动 `:game` 时切换目录。进程内 SharedPreferences 有缓存，不能在旧游戏进程仍运行时替换模块。`HxzRuntimeAssets` 校验 canonical path 仍位于私有模块目录；`RuntimeUtils` 的打开、目录枚举、版本判断和安装输入统一经过该接口。社区包名下缺少模块会明确失败，不把缺失的 version 文件当成已安装。旧 standalone fork 的资产读取继续使用 APK assets。

账号仍由 `content://top.hxzmc.community.game-account` 在本机提供。宿主允许同包同 UID 的调用，认证令牌不交给网页、不进入模块文件或房间清单。

## 模块格式与构建

`scripts/package-gameengine-runtime.mjs --out=... --version=... --build=...` 从维护 fork 的源码资产和 vendor AAR 收集运行资源，只保留 ARM64 natives 与 `bin-arm64.tar.xz`。生成文件名 `HXZ-Runtime-<version>-<build>-arm64.zip`。运行模块不含 AndroidManifest、DEX、Android 资源表或独立应用入口。

内层 `module.json`：

```json
{
  "schema": 1,
  "kind": "hxz-runtime-assets",
  "interfaceVersion": 1,
  "abi": "arm64-v8a",
  "minSdk": 29,
  "versionName": "0.8.4",
  "versionCode": 80400,
  "upstreamCommit": "efe4dcc5dbc78c55be177c330239e12845ae7ccf",
  "files": [{"path":"app_runtime/...","size":123,"sha256":"..."}]
}
```

所有归档成员必须与清单完全一致，除 `module.json` 外仅允许 `app_runtime/` 下的文件。宿主还需拒绝重复、链接、绝对路径、路径穿越与超出预算的条目，确认每个文件大小及 SHA-256 后再原子切换激活目录。外层可信签名必须先覆盖完整 ZIP 的 size/SHA-256，不能只信压缩包自带的清单。

指定 `--url=https://...` 后，使用原社区签名证书生成 `--out/updates/game-runtime-latest.json`。签名载荷有 `kind=android-runtime-module`、`package=top.hxzmc.community`、`interfaceVersion=1`、`abi=arm64-v8a`、版本、URL、size/SHA-256；与旧 `game-engine-latest.json` APK 更新通道分开。打包脚本不上传、不激活线上更新、不改变版本文件。

构建顺序：

```text
node mobile/game-engine/apply-adaptation.mjs
node mobile/game-engine/prepare-embedded.mjs
gradle -p mobile/android :app:assembleDebug
```

JDK 21、Gradle 8.14.4、SDK 35、AGP 8.13.2、Kotlin 2.4.10、R8 9.4.17，NDK r30。保留原版权与依赖许可；发布单 APK 的对应源码需要包含社区、FCL 完整维护 fork、构建脚本和所有适用许可，不能仅提供本目录的补丁来替代 GPL 对应源码。

## 房间桥

`job.expectedGame` 放在顶层；`options.joinServer` 仅允许 `127.0.0.1:<1..65535>`，覆盖服务器地址。`options.hostLanPort` 使用现有 `resources/direct-lobby/direct-lobby.jar`；该 agent **忽略 premain 的参数**，实际每两秒读取游戏 cwd 的 `.hxzl/direct-lobby.properties`，要求文件更新时间在 35 秒内。因此 HxzRooms 每 10 秒刷新受控文件，注入专用 JVM agent，解析 `[HXZ-DIRECT] READY/WAITING/ERROR`。原有 JVM 参数保留，仅替换上轮本桥生成的 agent；房间地址/host 选项不持久化到正常启动设置。

`GameAccountProvider.call("roomState", null, Bundle)` 承接：`game` 为最终配置 JSON，`port/ready/error` 为世界开放状态，`poll=true` 询问房间是否仍有效；返回 `active=false` 后停止心跳并删除控制文件。`FCLBridge.onExit` 回报 `exited=true`，宿主停止房间或将其标为等待。游戏尚未进入单人世界时不能把房间标为 ready。

配置包含 `minecraft/loader/loaderVersion/modCount/mods/preset/platform/compatibilityPolicy`。`mods` 与 PC 相同：对启用的 `mods/*.jar` 逐一 SHA-256，散列排序后用换行连接，再整体 SHA-256；空清单为 `""`。Minecraft 和加载器版本必须精确一致。PC/Android 的同一个默认 preset 可记录已登记的安卓平台适配差异并继续；未知包、不同 preset、同 Android 模组差异仍拒绝。`platform=android`、`compatibilityPolicy=hxz-android-1` 用来约束这条例外，不能放宽 PC 与 PC 的校验。

## 验证记录

`:hxzRuntime:assembleDebug --offline` 已完整成功；产物 AAR 核验包含编译后的代码、资源、manifest 和 ARM64 JNI，不含 `app_runtime`。最终宿主 APK 仍需与账号、模块安装和联机服务的整合一起完成编译及合包审计。未使用设备。

本地模块拆分样本为 71 个运行文件，展开约 146.9 MB、ZIP 约 129.4 MB；只代表当前固定源码。已逐项核验归档文件集合、SHA-256、大小和 ARM64 筛选，且没有 Android APK/Dex/Manifest。当前 APK 原生库保持静态以保留标准 Android linker namespace，不宣称任意外部 JNI 均可动态加载。

`node scripts/tests/android-runtime084.mjs` 直接编译实际 HxzRooms 和 HxzRuntimeAssets，跨 Java/Node 核验 PC 相同模组指纹、loopback 地址约束、平台适配例外及严格拒绝、房主必须获得明确 active 许可、实际 agent 日志解析，以及私有 generation 读取、路径穿越/越界/未激活拒绝、旧 APK 资产回退。Android 框架对象在 JVM 测试中使用窄 stub，此测试不证明 Android Activity、GPU 或真实 P2P 已在设备运行。宿主 APK 合并/编译结果后续记录于本轮总验收文档。
