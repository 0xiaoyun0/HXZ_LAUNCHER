研究日期：2026-10-21。状态：设计研究与废弃接入审计；尚未实现或验证独立游戏运行链路。本轮遵循用户“不实机测试”的要求。社区功能、同包模块验证与自行编写的联机大厅继续维护。

## 决策与独立性约束

用户要求参考已有启动器的行为，独立编写专用实现。此前将 FCL fork 编译为 Android library 的方案已废弃。GPL 是否允许复用，与用户是否接受复用，是两个不同条件；即使许可证允许，本次也不能复制、翻译、改名或包装 FCL 启动器源码来满足“独立实现”。

新实现需要自行完成 Android 宿主、生命周期、触控设置、账号交接、实例计划、进程监督和 JNI glue。可以评估独立第三方基础库，但必须从实际拥有该库的上游取得源码与许可，固定提交、构建参数和散列；不能把 FCL vendor AAR 的文件名当作来源证明。已阅读 FCL 实现的事实应保留在工程记录，不宣称经过严格的隔离式 clean-room 流程。

## 最小可行结构与接口

建议把变化最多的 JVM、窗口和实例适配放在明确的 seam。宿主的外部接口保持小规模：`prepare(job) -> LaunchPlan`、`start(plan, surface)`、`input(event)`、`resize(surfaceGeneration,width,height)`、`stop(reason)`；状态包含阶段、错误码、退出码和不含令牌的日志句柄。这里是接口提案，不是现成实现。

1. **实例计划模块**：读取本项目实例元数据，校验已安装版本、依赖和加载器，再形成不可变 LaunchPlan。计划包含 JVM 版本、main class、classpath、jvm/game 参数、native 搜索目录、实例目录、渲染器、资产和日志目录；令牌只在私有进程交接中短期提供，不写计划文件或日志。安装流程不能以残留 version JSON 充当成功。
2. **运行资产模块**：负责签名、ZIP/逐文件散列、限制解压、私有 generation 激活和回滚。此模块就绪只代表文件校验通过，另有 runtime capabilities 表明 JVM、窗口和目标游戏组合是否验证。接口 1 的旧 `app_runtime/**` 目录并非独立后端必须遵循的设计，不应让旧 FCL 布局反向规定新实现。
3. **Android 游戏模块**：自行编写社区包下的 Activity/SurfaceView，manifest 私有 `:game` 进程、`exported=false`。`:game` 是同 UID 应用进程，不是 `isolatedProcess=true`；需要读取实例私有文件和使用宿主权限。进程退出后必须通知主进程清理房间与隧道。Android 官方定义了私有冒号进程名的行为。[Activity process](https://developer.android.com/guide/topics/manifest/activity-element#proc)
4. **JNI 启动模块**：独立 C/C++ 实现加载已审计的 Android JVM，严格分离 ART 与游戏 JVM 的 JavaVM/JNIEnv、线程、对象和异常；把游戏 stdout/stderr 导入私有日志；每次启动使用新的游戏进程，不承诺在同一进程销毁后重启 HotSpot。宿主基础库随 APK 提供，首次下载只承载已定义并验证的依赖。
5. **窗口与输入模块**：Surface 生命周期、ANativeWindow 引用计数、GL context 所在线程和输入队列自行实现。跨 JNI 不传另一套 VM 的 jobject；只传 POD、字节或自己管理的 native 句柄。保留鼠标抓取、按键释放、IME、触控映射、分辨率和手柄设置行为，但界面与实现独立编写。
6. **房间模块**：主进程拥有连接和房间许可，游戏进程只能请求设置实际实例指纹、报告端口/ready/error/exit。joinServer 只接受本机受控隧道端口；hostLanPort 由 active 许可与退出清理控制。同包 provider 是状态通道，不直接证明世界已开放。

## JVM：Invocation API 是入口，兼容层仍需证明

JNI 规范提供 `JNI_CreateJavaVM` 和通过新 VM 的 JNIEnv 调用 main 的方式，建议另起 native 线程并配置足够栈空间；JNIEnv 只在所属线程有效。规范同时明确不支持一个进程创建多个 VM。Android JNI 文档也按每进程一个 JavaVM 的模型说明。因此“Android Activity 内 dlopen libjvm 然后调用 CreateJavaVM”不能仅凭标准文档判定受支持或可运行；ART 已在该进程中存在。必须以指定 Android OpenJDK 构建验证符号解析、TLS、信号处理、崩溃处理和线程归属，不可混用两套 JNI 表。这里并未断言工程上绝对不可能，只将其标为超出官方保证的首要验证项。[JNI Invocation API](https://docs.oracle.com/en/java/javase/21/docs/specs/jni/invocation.html)、[Android JNI tips](https://developer.android.com/ndk/guides/jni-tips)

JVM 必须针对 Android bionic/ABI 构建；普通 Linux aarch64 的 glibc JRE 不是等价物。Pojav 的 Android OpenJDK 构建仓库提供可追溯的候选研究起点，但该仓库已归档；它不是“复制 FCL 文件”的豁免，也不能证明当前 JDK21/Android35/16KiB 页组合可靠。应选择精确提交，审查所有补丁及外部下载，记录完整源码、工具链和许可，再分别构建验证。[Android OpenJDK 构建仓库](https://github.com/PojavLauncherTeam/android-openjdk-build-multiarch)

Android 10 对 target29+ 禁止直接 execve 应用 home 中的文件，并约束 text relocation/可执行映射。因此不能把私有目录下载的 `bin/java` 当作普通桌面可执行程序启动。若考虑 APK 自带 native executable 的新进程以避免 ART 共存，还需单独证明启动、窗口传递、linker 和存活管理；它是另一项研究方向，不是已完成替代方案。动态加载也不能靠 chmod 绕过平台限制。[Android 10 执行限制](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission)

## 窗口、LWJGL 与渲染

ANativeWindow 是 Android Surface 的 native 对应物，NDK 可获取/释放该引用；EGL/OpenGL ES、Vulkan 等公共 NDK 接口是独立窗口层的合法技术起点。它们并不提供 GLFW 的全部语义。Surface 销毁时先停止使用旧 EGLSurface 并同步渲染线程，再释放 window；重建时由 generation 防止迟到输入或回调操作旧句柄。此处的时序是设计约束，必须通过实现与运行验证。[ANativeWindow](https://developer.android.com/ndk/reference/group/a-native-window)、[NDK native APIs](https://developer.android.com/ndk/guides/stable_apis)

GLFW 官方平台列表为 Win32、Cocoa、Wayland、X11、Null，没有 Android。LWJGL 官方 Platform 源码枚举也没有 Android。Null 平台不是 Android 屏幕、IME 或输入实现，设置 `os.name=Linux` 也不会产生 Android native 库。实际要么从可审计的独立 Android 移植上游复用并明确归属，要么自行实现所需 GLFW ABI/回调、LWJGL native 构建与 Android platform 适配。不能用几个空方法或返回成功的 stub 宣称可运行 Minecraft。[GLFW 平台文档](https://www.glfw.org/docs/latest/intro_guide.html)、[LWJGL Platform 源码](https://github.com/LWJGL/lwjgl3/blob/master/modules/lwjgl/core/src/main/java/org/lwjgl/system/Platform.java)

Pojav 的 LWJGL fork 是独立第三方候选研究对象，仍须追踪 Android 修改是否依赖该启动器专有 CallbackBridge/native 入口，不能只复用 jar 后假定 ABI 满足。该仓库已归档。需要把允许复用的第三方部分与必须独立编写的 HXZ 宿主 glue 明确列出。[Pojav LWJGL fork](https://github.com/PojavLauncherTeam/lwjgl3)

桌面 OpenGL 与 OpenGL ES 并不等同。GL4ES 上游说明的目标主要是 OpenGL2.1/1.5 到 GLES2/1；不能把它概括为任意现代 Minecraft/模组的 OpenGL 满足条件。Zink 通过 Vulkan 实现桌面 OpenGL，但功能级别还取决于 Vulkan driver 能力，需要按 profile/扩展检查，不是仅检查设备支持 Vulkan。现代目标版本应先固定一个渲染路径和可验证的功能基线，再谈多渲染器设置。[GL4ES 上游](https://github.com/ptitSeb/gl4es)、[Mesa Zink](https://docs.mesa3d.org/drivers/zink.html)

LWJGL 还涉及 native 调用生成器、libffi、STB、OpenAL；游戏/模组可能依赖 JNA、AWT/java.desktop、字体、Java Sound 或桌面 native。安装器 JVM 与游戏 JVM 应分开验证。JNI main 成功只证明计算入口，GLFW 测试成功只证明窗口样例，都不等于 NeoForge/Forge 和现有三服模组可运行。

## 验证门槛与当前可宣称的结果

| 顺序 | 必须完成的证据 | 不能由此前证据替代的部分 |
| --- | --- | --- |
| 1 | 独立 native bridge 编译；固定 Android JVM 的简单 Java main 能输出、返回、正确处理异常并终止游戏进程 | 桌面 JVM 单测不能验证 ART/HotSpot 共存和 bionic loader |
| 2 | Surface/EGL 原生三角形，旋转/后台恢复、context 丢失、退出释放均正确 | 单纯 Activity 显示不能证明 GL 工作 |
| 3 | 目标 LWJGL + GLFW API 样例有真实画面、键鼠/IME/触控和音频 | stub 的符号存在不能证明行为 |
| 4 | 固定 vanilla 游戏版本到标题/世界、退出、再次启动 | JNI main 成功不能证明 Minecraft |
| 5 | 固定 loader/安装器与实际整合包的逐项验证 | 空实例或版本 JSON 不能算已安装目标包 |
| 6 | 同端/跨端房间与 direct-lobby ready/退出/断网恢复 | P2P 信令成功不能证明游戏协议与模组兼容 |

本轮不进行设备测试，因此只能报告接入撤销、文档与静态/编译证据。当前没有独立 Android 游戏后端完成的证据；UI 应明确显示尚缺的运行能力，不能把签名模块“installed”自动等同于游戏可启动。不会发布废弃 AAR、FCL 资源 ZIP 或伪装成独立实现的模块。
