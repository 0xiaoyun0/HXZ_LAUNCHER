# 安卓 80419：实例化绘制与原始加载错误

## 两份报告对应不同问题

第一份为 Minecraft 1.21.1 / NeoForge。渲染线程仍在 `limitDisplayFPS`，工作线程等待任务；`Cowardly refusing … broken mod state` 说明加载器此前已记录错误，并不能据此判断具体模组、DNS 或内存问题。Yuushya 缺材质警告也不足以认定该模组是根因。

第二份已经进入世界并发出聊天，Fabric 调用栈停留在 `GL32C.glDrawElementsInstancedBaseVertex`。两次采样相隔约 809 ms，渲染线程累计 CPU 增加约 747 ms，不能认定为 Java 锁死。Realms 报错与 Android 原生鼠标图标警告不能解释水体三角面错乱。

## 绘制修复

核对已使用的 [FCL NG-GL4ES 源码](https://github.com/FCL-Team/NG-GL4ES/blob/472f55e549e2bc76c87454905db52661c3cf57a9/src/gl/drawing.c)。其 GLES 基础顶点仿真在短索引中叠加 `basevertex`，会发生 16 位回绕。80417 仅修补普通绘制和批量绘制；用户这次使用的实例化路径没有接入修补。

80419 在实际 LWJGL/GLX 解析入口增加 core/ARB/EXT/OES 实例化入口，复用有界索引扩展。依旧使用 `glDrawElementsInstanced`，完整保留实例数量及属性除数，绘制后恢复原 EBO，不修改原始索引。零实例、负偏移、非三角形、映射中缓冲区、越界索引和 primitive restart 路径交回原驱动处理。不添加不可靠的索引缓存，不更换 EGL 呈现，不读取帧缓冲像素。

`scripts/tests/android-ng-render084.mjs` 编译生产 `hxz_fcl_render.cpp`，使用模拟 GL 缓冲区验证。新实例化用例在修补前稳定失败，修补后验证跨越 65,535、七个实例、字节索引、别名入口、状态恢复和边界降级，原有 12 项索引测试继续通过。这能确认适配层行为，不能代替手机 GPU 场景测试或宣称所有渲染异常均已解决。

## 原始加载错误

对 [NeoForge 的连带错误说明](https://github.com/neoforged/NeoForge/issues/2636) 所述情形，避免让重复错误取代真正的加载原因：

- 仅在手动诊断且日志已出现 broken mod state 时，请求游戏 JVM 读取已加载的 `ModLoader.getLoadingErrors()`，记录可用的关联模组、文件、错误参数及嵌套异常。不会主动加载 FML、清除错误或放行损坏状态。
- 读取失败时保留日志证据；对连带报错有界扫描最多 1,600 万字符的早期日志，默认正常运行仍只读取末尾。内存和输出均受限，过长整行省略，避免切断凭证后绕过脱敏。
- 先对来源脱敏，再制作不超过 4,800 字符的报告；原始错误排在普通等待线程前，两次渲染线程采样仍保留，完整脱敏报告保留本机。

`android-loader-issues084.mjs` 使用本机只读 FML 4.0.44 JAR，在桌面 HotSpot 中加入测试错误，验证按需读取文件、参数及嵌套原因，普通请求不读取加载错误，错误记录未被清除。`android-live-diagnostics084.mjs` 验证最初错误在大量连带报错及 18 KB 日志末尾之外仍可显示。网络会话与生产脱敏测试继续通过。

这部分修复了证据丢失；尚未获得用户手机最初的模组加载异常，不能宣称其责任模组已被修好，也不因本次日志批量禁用 Yuushya、航空学或其他玩法组件。
