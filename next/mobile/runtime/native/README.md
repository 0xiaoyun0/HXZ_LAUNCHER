# HXZ Android GLFW C ABI adapter

This backend implements the public GLFW 3.4 C ABI independently for the game's single Android window. `include/glfw3.h` and `include/LICENSE-GLFW.txt` are the unmodified upstream interface and license. The adapter source does not use launcher bridge code. The [GLFW window](https://www.glfw.org/docs/3.4/group__window.html) and [input](https://www.glfw.org/docs/3.4/input_guide.html) references define its callback and context behavior.

`hxz_configure_renderer(absoluteVerifiedPath, "osmesa")` loads an OSMesa provider dynamically in the game executor. `glfwCreateWindow` creates the requested desktop OpenGL context, and `glfwMakeContextCurrent` binds it on the game thread. `glfwSwapBuffers` finishes GL work and writes a completed RGBA frame to the shared-frame sink. The ART host posts rows to its Android Surface, honoring the native buffer stride and OSMesa's pixel origin. Resizing replaces the OSMesa buffer while its context stays on the owning thread. The caller must verify the provider library and its license/source before invoking this API.

`hxz_configure_renderer(pathOrNull, "egl")` supports only an explicit OpenGL ES 3.0 request. It uses a pbuffer while no Android Surface exists, then binds an EGL window surface on the game thread after each Surface generation change. It rejects desktop OpenGL requests, so EGL ES3 cannot masquerade as Minecraft's desktop OpenGL context. Renderer configuration, creation, binding, allocation and present failures return/report actual errors.

The host lends `ANativeWindow*` to `hxz_surface`; this module acquires its own reference until replacement or termination. The host starts a private `SOCK_SEQPACKET` endpoint and two `ASharedMemory` frame slots. After a same-UID `SO_PEERCRED` check, the native executor receives the frame descriptor using `SCM_RIGHTS`; no Surface pointer crosses the process boundary. Packets have fixed length, magic and version. Frame packets validate slot, dimensions, stride and sequence before presentation. A slot cannot be overwritten until acknowledged; full slots drop new frames. The Surface call and frame presentation stay on ART's native receiver thread, without JNI calls from the game process. The initial width and height bound later resize messages; larger changes require a new session. The host forwards key, button, cursor, scroll, Unicode and focus events as documented in `hxz_glfw.h`. The game queue is bounded to 512 entries, coalesces consecutive pointer/resize events and synthesizes releases for delivered pressed inputs on overflow. `hxz_release_inputs` should be called on focus loss, touch cancellation and pause. Captured-cursor state returns with each frame.

The native executable accepts either an installer job (`job`) or a game job (`job socket absolute-renderer-path osmesa`). It links `libhxz_runtime.so`, the same library that LWJGL GLFW opens, and sets `PR_SET_PDEATHSIG` before creating HotSpot. LWJGL OpenGL should use its [documented OSMesa path](https://github.com/LWJGL/lwjgl3/blob/master/modules/lwjgl/opengl/src/main/java/org/lwjgl/opengl/GL.java): `-Dorg.lwjgl.opengl.contextAPI=OSMesa` and `-Dorg.lwjgl.opengl.osmesa.libname=<absolute provider path>`. This avoids claiming a GLX context.

The context belongs to the thread that calls `glfwMakeContextCurrent`. Window destruction requires that thread to release it first. Joystick, custom system cursors, gamma control and Vulkan return explicit unavailable results. This is a single-window backend; its `glfwGetPlatform` result is GLFW's public `GLFW_PLATFORM_NULL` marker because GLFW 3.4 has no Android platform enum. ABI export coverage is not a claim of full desktop GLFW semantics.

`node mobile/runtime/test/hxz-glfw-abi084.mjs` cross-compiles and links an arm64 Android shared library with warnings as errors and checks all 124 functions declared by the official GLFW 3.4 header plus ten host hooks. `node mobile/runtime/test/hxz-native-ipc084.mjs` links the whole runtime and executable, checks JNI entries and confirms the executable depends on that runtime. These checks do not test device IPC, an actual OSMesa binary, Android Surface pixels, GL capabilities, frame rate or Minecraft startup. Those require the upstream renderer artifact and later manual device acceptance.
